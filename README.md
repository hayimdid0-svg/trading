# 증권 도메인 101 — QA 관점 단계별 학습 카드

증권 도메인을 QA 관점에서 처음부터 쌓기 위해 만든 학습용 웹 앱입니다.
용어 사전이 아니라, **개념 → 장애 시나리오 → QA 확인 포인트**가 한 줄로 이어지도록 카드를 설계했습니다.

배포: https://trading-wpterj4bran6ydbxhajqb9.streamlit.app/

## 왜 만들었나

증권 도메인 자료는 대부분 투자자용이거나 실무자용입니다. 투자자용은 "어떻게 돈을 버는가"를 설명하고, 실무자용은 이미 도메인을 아는 사람을 전제합니다. QA가 필요한 건 그 사이인데, 어떤 개념이 어떤 품질 리스크를 만들고 그 리스크를 어떤 테스트로 잡는지를 다루는 자료가 없었습니다.

그래서 직접 정리했습니다. 기준은 하나였습니다. **이 개념이 틀리면 고객에게 무슨 일이 생기는가.** 증거금률 40%는 외워지지 않지만, 증거금 계산이 틀리면 고객이 못 살 주문을 내고 이틀 뒤 반대매매로 손실이 확정된다는 건 잊히지 않습니다. 개념을 기억하게 만드는 고리가 리스크라고 보고, 모든 카드에 그 고리를 넣었습니다.

## 카드 스키마

카드 한 장은 아래 구조를 가집니다.

`one_liner`로 한 문장 멘탈모델을 잡고, `analogy`로 일상 비유를 붙입니다. `where_in_app`은 그 개념이 MTS 어느 화면에서 실제로 보이는지, `common_confusion`은 초보가 버그로 오해하는 지점입니다. `if_wrong`에 고객 금전손실 여부와 구체적 파급을 적고, 거기서 도출된 `qa_checks`가 실제 확인 항목이 됩니다. 마지막으로 `quiz`로 판단력을 확인하고, `next_level_hook`과 `simplified_away`로 다음 단계와 연결합니다.

`simplified_away`는 의도적으로 넣은 필드입니다. Lv0에서 "예수금으로 주식을 산다"고 설명하면 증거금·대용금·신용융자를 숨기게 되는데, 무엇을 숨겼는지 기록해두지 않으면 상위 레벨에서 회수할 수 없습니다. 테스트 범위를 명시하고 제외한 부분을 잔여 리스크로 남겨두는 것과 같은 발상입니다.

## 퀴즈 설계 기준

퀴즈는 정답 암기가 아니라 판단을 묻습니다. 세 가지 기준을 지켰습니다.

첫째, 답이 하나로 떨어져야 합니다. 둘째, 상위 레벨 지식 없이 그 레벨 개념만으로 풀려야 합니다. 셋째, 결론이 고객의 주의가 아니라 시스템 요건으로 향해야 합니다.

이 기준은 처음부터 있던 게 아니라, 초안 퀴즈를 검토하다 세 번 다시 쓰면서 만들어졌습니다. 어떤 종류의 문제였는지 기록해둡니다.

**L0-001** 초안은 "이체 후 홈은 100만원, 주문 화면은 0원. 버그인가?"였고 답이 "둘 다 가능"이었습니다. 답이 갈리면 학습자에게 남는 게 없어서, 전제조건을 못 박아 답이 하나로 떨어지게 고쳤습니다. → 기준 1이 여기서 나왔습니다.

**L0-002** 초안은 "오류 후 주문 버튼을 다시 눌러도 되는가?"였고 답이 "안 된다"였습니다. 그러면 중복 방지 책임이 고객에게 넘어가는데, 운영환경에서는 고객이 몇 번을 누르든 시스템이 1건으로 처리해야 합니다. 질문을 "거래소 접수 여부를 판단할 수 있는가?"로 바꿔 결론이 시스템 요건으로 향하게 했습니다. → 기준 3이 여기서 나왔습니다.

**L1-004** 초안은 "거래가 체결됐는데 고객 주문은 미체결로 남았다"였습니다. 시장 전체의 체결과 내 주문의 체결을 구분하지 않아, 같은 주문이 체결이면서 미체결인 것처럼 읽혔습니다. 숫자를 넣어 "70,000원에 5,000주가 거래됐는데 고객의 100주는 체결되지 않았다"로 다시 썼습니다. 재현 조건이 한 줄이라도 모호하면 개발자와 QA가 서로 다른 상황을 떠올린다는 걸 스스로 확인한 사례입니다.

## 레벨 구성

**Lv0 · 돈과 주식이 어디로 움직이나** (3장, 완료)
용어 암기 없이 거래의 3단 구조를 이해합니다. 예수금, 증권사와 거래소의 역할 분담, 주문·체결·결제가 서로 다른 사건이라는 것까지. 졸업 조건의 핵심은 "숫자가 안 맞는 기간이 정상적으로 존재한다"를 설명할 수 있는 것입니다. 언제 안 맞아도 되는지를 알아야 언제 맞아야 하는지를 테스트할 수 있습니다.

**Lv1 · 주문 한 건의 생애주기** (8장, 완료)
호가창, 지정가와 시장가, 체결 우선순위, 부분체결, 정정, 취소, 주문가능금액 예약. 목표는 주문 상태 전이도를 직접 그릴 수 있는 수준입니다. QA가 실무에서 가장 많은 시간을 쓰는 영역이라 카드를 가장 두껍게 넣었습니다.

**Lv2 · 시간이 만드는 규칙** (예정)
동시호가, 정규장, 시간외단일가, VI, 거래정지, 휴장, 그리고 T+2 결제와 D+2 예수금. "잔고에 주식은 있는데 왜 출금이 안 되나"를 설명할 수 있으면 통과입니다.

**Lv3 · 빌린 돈과 여러 시장** (예정)
증거금률, 미수, 반대매매, 대용금, 신용융자, NXT 출범 이후의 복수시장과 SOR·최선집행의무, 해외주식의 환전과 서머타임.

**Lv4 · 시스템과 규제** (예정)
주문 순서보장과 멱등성, 원장과 실시간 시세의 정합성, 주문 피크 TPS와 성능 게이팅, 전산장애 보상기준, 전자금융감독규정과 감사증적.

## 실행 방법

```
pip install -r requirements.txt
python -m streamlit run learn.py
```

카드 데이터는 `data/lv*.yaml`에 있고 앱 코드와 분리돼 있습니다. 파일을 추가하면 레벨이 자동으로 목록에 붙습니다. 내용 수정과 화면 로직 수정이 서로를 건드리지 않게 하려고 이렇게 나눴습니다.

## 한계와 앞으로

카드에 적힌 규정성 수치(호가단위, 시장가 잔량 처리, 정정 우선순위, 증거금률 등)는 거래소 규정과 증권사 정책에 따라 달라지고 개정됩니다. 현재 카드는 확인이 필요한 항목을 `common_confusion`에 명시해뒀고, 각 항목에 출처와 확인 날짜를 붙이는 작업이 남아 있습니다. Lv3의 NXT·SOR 관련 내용은 특히 최신 공지로 검증이 필요합니다.

읽기 중심 구조라 인터랙션이 없다는 것도 한계입니다. 호가창 시뮬레이터, 주문 상태 전이도, 예수금 날짜 슬라이더, 증거금·반대매매 계산기를 레벨별로 붙이는 것이 다음 단계입니다.
